A organização de schema, configuração e geração automática do Client segue a

Os comandos de desenvolvimento, build, tipos e testes geram o Client por conta
própria, sem etapa manual prévia. A divisão por domínio preserva a migration inicial.

### Operação local e testes

Copiar `.env.example` para `.env` e preencher senhas locais distintas com valores
aleatórios. Usar o usuário/banco `kaizen_local`, porta 5432, nas URLs de runtime e
migration; usar `kaizen_test`, porta 5433, nas duas URLs de teste. O Compose exige
senhas configuradas, publica somente em loopback e mantém o banco de teste em
memória, separado do volume de desenvolvimento. Não publicar `.env` nem copiar
credenciais de produção para a máquina local.

```powershell
docker compose --profile test up -d --wait
pnpm install --frozen-lockfile
pnpm db:validate
pnpm db:generate
pnpm db:deploy
pnpm db:status
pnpm test:integration
pnpm run ci
```

`db:generate` não exige URL/conexão; executá-lo antes de tipos, testes e build em
checkout limpo. O Client é gerado em `src/generated/prisma`, ignorado pelo Git,
lint e formatação. Os testes React continuam em jsdom; integração usa Node e
PostgreSQL real, aplica migrations automaticamente no banco de teste e desfaz
as fixtures sintéticas por rollback de transação. Não faz truncate/reset nem
altera o banco local de desenvolvimento. As URLs de teste devem ter o mesmo
destino loopback e o nome exato `kaizen_test`.

Para evolução do schema, usar `pnpm db:migrate --name descricao` somente no
ambiente local, banco `kaizen_local`, revisar SQL antes da entrega e gerar o
Client novamente. `db push` e reset não fazem parte do fluxo. O `tsx` só será
adicionado na E05-T03, junto do CLI consumidor.

### Fronteira do servidor e deploy

`src/lib/db/environment.ts` valida somente a configuração necessária ao banco;
`src/lib/db/client.ts` é lazy e server-only, usa adapter pg, pool limitado e
reutiliza o Client por processo (também por hot reload fora de produção).
Importar esses módulos não conecta o banco. Nenhuma tela consome Prisma nesta
tarefa. URLs de runtime não são expostas por `NEXT_PUBLIC_*`, DTOs ou logs de
queries. Fora do local, o runtime exige `sslmode=verify-full`, sem desabilitar
verificação de certificado. A configuração Prisma usa somente `DIRECT_URL`,
sem fallback para a URL pooled.

Em CI, aplicar `migrate deploy` em PostgreSQL 18.6 descartável antes dos testes.
Os jobs de qualidade, testes e build geram Client explicitamente. Publicação em
preview/produção e provisionamento de roles/Neon permanecem em E08; a role de
runtime deverá receber apenas privilégios necessários, sem UPDATE/DELETE de
definições, separada da role de migration. Owner é permitido somente nos bancos
locais/descartáveis da tarefa.

### Recuperação de migrations

A migration inicial usa transação SQL: falha na DDL não deve deixar metade do
schema aplicado. Se falhar, investigar no banco descartável, corrigir antes da
primeira aplicação compartilhada e testar novamente. Não usar `migrate resolve`
para declarar sucesso sem conferir o estado real. Depois de aplicada em ambiente
compartilhado, uma migration nunca é editada/apagada: a correção é uma nova migration.
Rollback de aplicação exige código compatível; alteração destrutiva usa expand/
contract e backup/restore validado, sem exclusão automática de volume ou histórico.

[GHSA-rgwj-5xj2-c3m3](https://github.com/advisories/GHSA-rgwj-5xj2-c3m3).

[GHSA-ggr8-5vv4-36mx](https://github.com/advisories/GHSA-ggr8-5vv4-36mx).

Compatibilidade confirmada por merge de objetos, carregamento real da configuração,
regressão de grafo circular e gates completos em `developer` e na composição
E05-T02, incluindo PostgreSQL real. Auditoria não encontra vulnerabilidades.
Não houve upgrade Prisma RC ou exclusão de advisory. Remover cada override
temporário quando seu pai estável incorporar a respectiva correção; mudanças
futuras de configuração exigem revalidar o contrato de mesclagem.

## E05-T06 — Implementar acesso pessoal

Dependência: E05-T05. Esta tarefa é gate obrigatório de E06 e E07.

Adicionar:

- `src/lib/security/session.ts` com JOSE e cookie autenticado;
- `src/lib/security/authorization.ts` para exigir o proprietário e derivar `workspace_id` no servidor;
- `src/lib/security/origin.ts` para validar `Origin`/`Host` em mutações;
- `src/lib/security/rate-limit.ts` com limite persistido para tentativas de pareamento;
- `src/app/ativar/page.tsx` e Server Action de pareamento;
- testes de sessão ausente, inválida, expirada, rotacionada, origem inválida e workspace forjado;
- script/configuração necessária para gerar hash da chave sem registrar o segredo.

Instalar `jose@6.2.10`. Em HTTPS, o cookie usa prefixo `__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax` e `Path=/`; no HTTP local, usar nome separado sem `Secure`, nunca enfraquecer preview ou produção. A chave de edição possui 32 bytes aleatórios e somente seu hash entra no ambiente. `SESSION_SECRET` possui ao menos 32 bytes. Nenhum valor real entra no Git, PR ou log.

A tarefa só termina quando a Data Access Layer e as mutações possuem uma API de autorização testada que E06/E07 possam consumir. Ela não publica ambiente externo.
