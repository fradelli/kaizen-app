# E05 — Banco, importação e acesso pessoal

## Status do pacote

- **Uso:** ler somente durante tarefas deste épico.
- **Fonte:** decisões aprovadas de produto, arquitetura, dados e operação.

## Implementação

Os itens desta parte são especificações exatas de arquivos e gates. O código será produzido na tarefa correspondente após examinar os dados exigidos; nenhum bloco abaixo finge conter a classificação ainda não realizada dos exercícios.

Cada item de metadado precisa ter `exercise_id`, `measurement_type`, `load_applicable`, `load_unit` e `normalization_rule`. `load_unit` é `kg` quando aplicável e `null` quando não. A classificação precisa ser revisada exercício por exercício contra plano e biblioteca; categoria, nome e regex não podem definir carga silenciosamente.

O modelo deve conter as 18 entidades conceituais da arquitetura, incluindo `PairingRateLimit` e sem `User`/`Membership`. Toda tabela pessoal inclui `workspace_id`; versões importadas são imutáveis; execuções preservam a versão apresentada.

## E05-T04 — Integridade persistida

Adicionar testes de constraints para ownership, data, série, carga, campos alimentares incompatíveis, revisão concorrente e preservação histórica. Criar `scripts/validate-persisted-data.ts` para CI contra banco descartável. Não usar SQLite ou mock do Prisma.

## E05-T05 — Backup e restore

Criar `docs/operations/BACKUP-AND-RESTORE.md`, script de verificação sem credenciais e evidência de `pg_dump`/`pg_restore` entre dois PostgreSQL locais descartáveis. A tarefa termina quando o banco restaurado passa migrations, importação, contagens por workspace e validação estrutural. Neon, RPO/RTO gerenciado e backup externo permanecem em E08-T03/T04.

## E05-T06 — Implementar acesso pessoal

Dependência: E05-T05. Esta tarefa é gate obrigatório de E06 e E07.

Adicionar:

- `src/lib/security/session.ts` com JOSE e cookie autenticado;
- `src/lib/security/authorization.ts` para exigir o proprietário e derivar `workspace_id` no servidor;
- `src/lib/security/origin.ts` para validar `Origin`/`Host` em mutações;
- `src/lib/security/rate-limit.ts` com limite persistido para tentativas de pareamento;
- `src/app/ativar/page.tsx` e Server Action de pareamento;
- testes de sessão ausente, inválida, expirada, rotacionada, origem inválida e workspace forjado;
- script/configuração necessária para gerar hash da chave sem registrar o segredo.

Instalar `jose@6.2.10`. Em HTTPS, o cookie usa prefixo `__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax` e `Path=/`; no HTTP local, usar nome separado sem `Secure`, nunca enfraquecer preview ou produção. A chave de edição possui 32 bytes aleatórios e somente seu hash entra no ambiente. `SESSION_SECRET` possui ao menos 32 bytes. Nenhum valor real entra no Git, PR ou log.

A tarefa só termina quando a Data Access Layer e as mutações possuem uma API de autorização testada que E06/E07 possam consumir. Ela não publica ambiente externo.
